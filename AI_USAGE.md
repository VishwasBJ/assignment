## What Was Written / Decided Manually

1. **Review template system prompts** — the exact wording of the Security, Performance, and Code Quality prompts in `review-engine.service.ts` was iterated on manually. The AI's first draft was too generic; the final version explicitly names OWASP, N+1 queries, cyclomatic complexity, etc.

2. **Provider type list** — the decision to support exactly these five types (OPENAI, LM_STUDIO, OLLAMA, OPENROUTER, CUSTOM) was a deliberate choice, not AI-suggested.

3. **Storage-in-DB for files** — the AI suggested disk storage initially. This was overridden in favour of storing file content as `Text` in PostgreSQL to keep the app stateless and deployment-simple.

4. **Keyword retrieval instead of embeddings for chat** — the AI suggested a vector-based approach. This was rejected as over-engineered for the scope; a simple word-overlap score was chosen instead.

5. **`proxy.ts` instead of `middleware.ts`** — Next.js 16 deprecates `middleware.ts` and renames the convention to `proxy.ts` with an exported `proxy` function. This was caught by reading the in-package docs at `node_modules/next/dist/docs/` before writing any code.

6. **`params` as Promise** — Next.js 16 makes route `params` a `Promise`. The `[id]/page.tsx` consumes it with `React.use(params)`. This was discovered from the official layout/page API docs shipped with the package.

## Key Engineering Decisions & Reasoning

### Why PostgreSQL for file storage (not S3 / disk)?

Storing file content as `Text` in the DB means:
- Zero infrastructure dependency beyond the DB itself.
- Easy local dev — no bucket config needed.
- Simpler deployment — the app is fully stateless.
- Trade-off: not suitable for very large files or binary assets, but code files are small.

### Why strategy pattern for AI providers?

Every provider (OpenAI, Ollama, LM Studio, OpenRouter) exposes the same `/chat/completions` endpoint shape. By making `AiAdapterService` select the provider at runtime from the DB and call a single generic HTTP request, swapping providers never touches any business logic. Adding a new provider is a data change (insert a row), not a code change.

### Why Zustand instead of React Context for auth?

Zustand avoids the provider-wrapping overhead and re-render cascades of Context. The auth store is small (user + token + 3 actions) and never needs to be server-side — Zustand is the right scope.

### Why keyword retrieval for chat context?

Embedding-based retrieval (e.g. pgvector + OpenAI embeddings) would require:
- An additional API call per user message.
- A vector extension in PostgreSQL.
- Chunking/indexing logic.

For a codebase of tens of files, a simple word-overlap scorer finds the right file 90%+ of the time. It runs in microseconds with no extra dependencies.

### Why store `issues` as `Json` in Prisma?

The AI review output schema (issue fields) is likely to evolve as prompts are refined. Using `Json` avoids DB migrations for minor schema tweaks. The TypeScript types in `src/lib/types.ts` enforce the shape at the application layer.

## Prompts Used

The main prompt driving the entire project was the assessment brief's "Master Build Prompt" (see `build-prompt.md`). Key sub-prompts used during development:

- *"Read the Next.js docs in node_modules before writing any code"* — led to discovering the `proxy.ts` breaking change and `params` as Promise.
- *"Implement the strategy pattern for AI providers so swapping providers doesn't touch business logic"* — shaped the `AiAdapterService` design.
- *"Use keyword/file-relevance matching for chat, don't over-engineer with embeddings"* — set the retrieval approach.
- *"Store files in PostgreSQL as text, not on disk, for simplicity"* — overrode the default AI suggestion.
